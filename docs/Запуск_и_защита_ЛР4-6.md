# Запуск проекта и защита ЛР № 4–6

Инструкция написана под Windows (PowerShell), но команды легко переносятся в bash.
Все команды выполняются из корня проекта: `C:\Users\Ardor\Desktop\sirius_food`.

## 0. Подготовка (один раз)

```powershell
# 1. Docker Desktop запущен
docker --version

# 2. Python 3.10 и зависимости
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt

# 3. Конфигурация
copy .env.example .env
```

На этой машине порт `6379` занят локальной службой Redis 5.x, которая не понимает
RESP3. Поэтому в `.env` уже указано:

```text
REDIS_PORT=6380
REDIS_URL=redis://localhost:6380
```

Если у преподавателя/на другой машине 6379 свободен, можно оставить дефолт из
`.env.example` (6379) — `docker-compose.yml` читает `REDIS_PORT`.

```powershell
# 4. База и Redis
docker compose up -d db redis

# 5. Миграции
# Для чистой базы:
alembic upgrade head
# Если таблицы уже есть, а alembic_version нет:
alembic stamp a1b2c3d4e5f6
alembic upgrade head

# 6. Тесты (должно быть 91 passed)
$env:SQL_ECHO="false"
.\.venv\Scripts\python.exe -m pytest tests -q
```

## 1. Обычный запуск проекта

Нужны четыре процесса (четыре окна PowerShell):

```powershell
# Окно 1 — API
$env:SQL_ECHO="false"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000

# Окно 2 — Celery worker (на Windows обязательно --pool=solo)
.\.venv\Scripts\celery.exe -A app.core.celery_app worker --loglevel=info --pool=solo

# Окно 3 — Celery Beat (периодические задачи)
.\.venv\Scripts\celery.exe -A app.core.celery_app beat --loglevel=info

# Окно 4 — Flower (мониторинг, http://127.0.0.1:5555)
.\.venv\Scripts\celery.exe -A app.core.celery_app flower --port=5555
```

> **Ошибка `OSError: [WinError 10048]`** означает, что порт 5555 уже занят —
> скорее всего, другой Flower уже запущен. Найдите и остановите его:
> ```powershell
> Get-NetTCPConnection -State Listen -LocalPort 5555 | Select-Object OwningProcess
> Stop-Process -Id <PID> -Force
> ```
> Либо поднимите Flower на другом порту: `flower --port=5556` и откройте
> `http://127.0.0.1:5556`.

Проверка API: `http://127.0.0.1:8000/health` → `{"status":"ok","database":"ok"}`,
Swagger: `http://127.0.0.1:8000/docs`.

> Если в процессе демо упёрлись в `429` (rate limiting), можно сбросить счётчики:
> `docker exec sirius_food-redis-1 redis-cli FLUSHDB`.
> После этого кеш меню прогреется заново при первом запросе.

## 2. ЛР № 4 — кеширование: как показать

### Запуск двух инстансов API

```powershell
# Окно 1 — baseline «до кеша»: каждый запрос идёт в PostgreSQL
$env:CACHE_ENABLED="false"; $env:SQL_ECHO="false"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8010

# Окно 2 — рабочий инстанс с кешем (по умолчанию CACHE_ENABLED=true)
$env:SQL_ECHO="false"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8020
```

### Замеры Locust

```powershell
# 50 пользователей, 15 с — оба инстанса
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8010 --headless --only-summary -u 50 -r 10 -t 15s --csv docs/locust/baseline
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8020 --headless --only-summary -u 50 -r 10 -t 15s --csv docs/locust/with_cache

# 500 пользователей, 70 с — пик из методички
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8010 --headless --only-summary -u 500 -r 10 -t 70s --csv docs/locust/baseline_500
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8020 --headless --only-summary -u 500 -r 10 -t 70s --csv docs/locust/with_cache_500
```

### Веб-интерфейс Locust (как показать в браузере)

Headless-прогон нужен для цифр в README. Преподавателю удобнее показать живой
график. Запустите Locust **без** `--headless`:

```powershell
# Вариант с кешем — основной для показа
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8020 --web-host=127.0.0.1 --web-port=8089

# Второй терминал: baseline «до кеша», другой веб-порт, чтобы не конфликтовать
.\.venv\Scripts\python.exe -m locust -f locustfile.py --host=http://127.0.0.1:8010 --web-host=127.0.0.1 --web-port=8090
```

Откройте в браузере:
- `http://127.0.0.1:8089` — инстанс с кешем;
- `http://127.0.0.1:8090` — baseline.

`--web-host=127.0.0.1` важен на Windows: без него Locust слушает только IPv6
(`localhost`), и браузер по `127.0.0.1` не подключается. Если нужна сеть,
укажите `--web-host=0.0.0.0` и открывайте `http://<IP-машины>:8089`.

Что делать в окне Locust:

1. На стартовой странице `Number of users` = **50**, `Spawn rate` = **10**,
   `Host` уже подставлен из `--host`. Нажмите **Start swarming**.
2. Через 15–20 с откройте вкладки **Statistics** и **Charts**: видны RPS,
   медиана, 95-й перцентиль и график отклика. Покажите, что failures = 0.
3. Для пикового сценария нажмите **Stop**, затем снова **Start swarming** с
   `Number of users` = **500**, `Spawn rate` = **10**; подержите 60–70 с.
4. Во вкладке **Download Data** можно скачать `*_stats.csv` — это те же файлы,
   что лежат в `docs/locust/`.
5. **Stop** — обязательно остановить нагрузку перед показом Swagger/gRPC, чтобы
   она не мешала остальным демо.

Если порт 8089 занят, задайте другой: `--web-port=8091`.

## 3. ЛР № 5 — Celery: как показать

Достаточно окон: API (8000), worker, beat, flower (опционально).

### Сценарий

1. В Swagger или через HTTP зайти студентом `student@sirius.ru` / `Passw0rd!`
   (после `seed_lab6.py`; баланс можно пополнить в БД, если нужно несколько заказов).
2. `POST /orders/create` с `{"item_id": 4, "quantity": 1}` — ответ приходит за
   **десятки–сотни мс**, а не за 4+ секунды, как в MVP.
3. В логе воркера видно три задачи:
   `generate_order_pdf` (2 с), `send_order_email` (1 с), `send_order_sms` (1 с).
4. Заказ с `id % 5 == 0` «падает» на email — в логе видны ретраи
   `retry: Retry in 1s / 2s / ...`, затем сообщение попадает в DLQ.

Проверка артефактов:

```powershell
# Идемпотентность PDF: флаги в Redis
docker exec sirius_food-redis-1 redis-cli keys 'pdf_generated:*'

# Dead Letter Queue
docker exec sirius_food-redis-1 redis-cli lrange dlq 0 -1

# Статистика Beat (ключ пишется задачей collect_daily_order_stats)
.\.venv\Scripts\celery.exe -A app.core.celery_app call app.tasks.orders.collect_daily_order_stats
docker exec sirius_food-redis-1 redis-cli get stats:orders:2026-11-17
docker exec sirius_food-redis-1 redis-cli ttl stats:orders:2026-11-17
```

Замер времени ответа 17.11.2026: 448 / 128 / 72 / 82 / 84 мс (первый запрос —
прогрев соединения с брокером, далее 72–84 мс).

## 5. Короткий план ответа на защите

### ЛР № 4 (кеширование)

1. **Проблема**: обеденный пик, сотни пользователей читают меню; каждый запрос шёл в PostgreSQL.
2. **Решение**: Cache-Aside в `app/modules/menu/repository.py`: hit → Redis, miss → БД + TTL.
   Кеш именно в Repository, а не в Service — чтобы бизнес-слой не зависел от инфраструктуры.
3. **Надёжность**: distributed-лок от cache stampede; fail-open при падении Redis;
   событийная инвалидация после POST/PATCH; прогрев кеша на startup.
4. **Критерий 10**: у категорий TTL 10 мин, у меню 5 мин — разные TTL; прогрев кеша.
5. **Замеры**: 50/500 пользователей, таблицы в README, CSV в `docs/locust/`.
6. **Честная оговорка**: при 500 соединениях узкое место — пул потоков одного воркера,
   поэтому эффект 20–24%, а не кратный.

### ЛР № 5 (Celery)

1. **Проблема**: PDF/email/SMS выполнялись синхронно в `POST /orders/create` — 4+ секунд.
2. **Решение**: бизнес-событие «заказ создан» → `.delay()` в `OrderService` → три фоновые задачи.
   HTTP отвечает за десятки–сотни мс.
3. **Надёжность**: JSON-сериализация (не pickle), `acks_late`, prefetch=1,
   ретраи 1–2–4 с с jitter, DLQ через `ReliableTask.on_failure`.
4. **Идемпотентность**: флаг `pdf_generated:<order_id>` в Redis (TTL 1 час).
5. **Beat**: `collect_daily_order_stats` раз в сутки, ключ `stats:orders:<дата>`.
6. **Мониторинг**: Flower.
7. **Честная оговорка**: `OrderService` импортирует задачи напрямую — это компромисс
   между чистой архитектурой и простотой публикации; задачи не содержат FastAPI.

### ЛР № 6 (gRPC-микросервис)

1. **Проблема**: модуль доставки вырос в отдельный сервис (Strangler Fig).
2. **Контракт**: `proto/delivery.proto` — **6 RPC = 4 unary + 2 streaming**:
   `AssignCourier`, `CompleteDelivery`, `GetMyDeliveries`, `GetDeliveryStatus`,
   `TrackDelivery` (server streaming), `ChatWithCourier` (bidi).
3. **архитектура**: FastAPI — HTTP-адаптер, `DeliveryGrpcClient` — клиент с DI через
   конструктор, бизнес-правила в `DeliveryService`, БД общая.
4. **Стойкость**: таймауты 5 с / 30 с, маппинг ошибок
   `UNAVAILABLE → 503`, `DEADLINE_EXCEEDED → 504`, `NOT_FOUND → 404`,
   `PERMISSION_DENIED → 403`, `INVALID_ARGUMENT → 400`.
5. **Проверено вживую**: `demo_lab6.py` (200/400/403 + SSE), `grpc_chat.py`,
   остановка сервера → 503, перезапуск → 200.
6. **Честная оговорка**: `assign_courier` пока не проверяет роль курьера и уникальность
   активной доставки на уровне контракта; это задел для следующего этапа.

## 6. Возможные вопросы преподавателя

* **«Почему кеш в Repository, а не в Service?»** — кеш это деталь хранения данных,
  ускоритель СУБД. Service не должен знать про Redis; AST-тест это проверяет.
* **«Что будет при падении Redis?»** — fail-open: приложение читает из PostgreSQL,
  кеш не создаётся, ошибки логируются. Приложение работает медленнее, но не падает.
* **«Как защита от одновременного промаха?»** — distributed-лок `menu:all:lock`,
  только один запрос идёт в БД, остальные ждут и читают прогретый кеш.
* **«Почему не pickle в Celery?»** — pickle позволяет выполнить произвольный код
  при подделке сообщения в брокере; у нас только JSON.
* **«Что с идемпотентностью PDF?»** — флаг в Redis, поэтому повторная доставка
  сообщения после падения воркера не создаёт второй чек.
* **«Почему 503, а не 500?»** — это осознанная сетевая ошибка availability;
  маппинг в клиенте отличает «сервис недоступен» от неизвестного сбоя.
* **«Почему порт 50061, а не 50051?»** — на Windows с Hyper-V диапазон
  50000–50059 зарезервирован; 50061 привязывается стабильно, без конфликтов.
