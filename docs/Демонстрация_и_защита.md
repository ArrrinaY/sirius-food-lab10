## 1. Проект за 60 секунд

«Сириус.Еда» — серверная часть приложения столовой колледжа на Python + FastAPI: студенты регистрируются, пополняют баланс, заказывают еду; повара видят очередь заказов на кухне; курьеры видят свои доставки; администратор назначает курьеров.

В проекте выполнены три работы:

| | ЛР № 2 (архитектура) | ЛР № 3 (безопасность) | ЛР № 4 (кеширование) |
|---|---|---|---|
| Исходная проблема | В MVP весь код был в одной куче: HTTP-обработка + бизнес-правила + SQL в одной функции | После рефакторинга система «открыта настежь»: запросы идут без проверки, кто их прислал | В обеденный пик сотни пользователей читают меню: каждый запрос бьёт в PostgreSQL, пул соединений переполняется, ответ растёт до секунд |
| Что сделано | Модули `orders`, `users`, `delivery` разделены на три файла: `router.py` → `service.py` → `repository.py`. Зависимости — только внутрь, через инверсию (конструктор + Protocol) | Внедрены JWT-токены, bcrypt, RBAC-роли, защита от IDOR, rate limiting на Redis, ограниченный CORS, Secure by Default | Cache-Aside в Repository (hit → Redis, miss → БД + запись с TTL), событийная инвалидация после мутаций, защита от cache stampede (distributed-лок), категория меню с TTL 10 минут и прогрев кеша на старте |
| Доказательство | unit-тесты на in-memory заглушках без СУБД; архитектурный тест импортов через AST | 91 проходящий тест; живые сценарии в Swagger: 401, 403, 429, ротация refresh-токенов | TTL ключей в Redis; событийная инвалидация — новое блюдо видно сразу после POST; замеры Locust «до/после» в README (50 пользователей: медиана 16 → 15 мс, 95-й перцентиль 56 → 45 мс; 500 пользователей: медиана 990 → 750 мс, RPS 267 → 313) |

Одна фраза на случай «в чём суть вашей работы»:

> «Сначала мы отделили бизнес-правила от фреймворка и базы данных, чтобы код можно было тестировать без запуска Postgres, а потом закрыли доступ к этим правилам от посторонних: аутентификация (кто ты) — по JWT, авторизация (что тебе можно) — по ролям и принадлежности объекта, плюс защита от подбора пароля и от повторного использования украденного refresh-токена».

## 2. Словарь простыми словами

| Термин | Что это | Аналогия |
|--------|---------|----------|
| **Clean Architecture** | Правило организации кода: зависимости направлены только внутрь — от фреймворка к бизнес-логике, никогда наоборот | Шеф-повар живёт своей жизнью, а кладовщик и официант подъезжают к нему по его правилам |
| **`router.py` (транспорт)** | Принять HTTP-запрос, проверить формат, вернуть JSON и код ответа | Официант: принимает заказ, несёт на кухню, вносит результат |
| **`service.py` (бизнес-логика)** | Бизнес-правила: «хватает ли денег», «чужой ли это заказ» | Шеф-повар: решает по правилам ресторана, собственных рук (SQL, HTTP) у него нет |
| **`repository.py` (инфраструктура)** | Работа с базой: SELECT / INSERT / UPDATE | Кладовщик: умеет класть и доставать, правил ресторана не знает |
| **Инверсия зависимостей (DIP)** | Сервис просит «что-то, что умеет сохранять заказы» (контракт), а конкретную базу ему передают снаружи через конструктор | Шефу всё равно, какой кладовщик в смене, — лишь бы понимал команды |
| **Protocol** | Python-контракт «каким должен быть репозиторий», объявлен прямо в `service.py` | Должностная инструкция кладовщика |
| **Аутентификация** | Ответ на вопрос «кто ты?» | Гардероб: показал паспорт — получил номерок (токен) |
| **Авторизация** | Ответ на вопрос «что тебе можно?» | Директор открывает серверную, студент — нет |
| **JWT** | Подписанный сервером «пропуск»: `header.payload.signature`. Payload виден всем (Base64), но подделать нельзя (подпись) | Заламинированный бейдж: фото прочитают все, фальсифицировать не выйдет |
| **Access-токен** | Короткоживущий пропуск (15 минут) для каждого запроса | Однодневный вход в здание |
| **Refresh-токен** | Долгоживущий (7 дней), чтобы получать новые access-токены без повторного ввода пароля | Абонемент на пропуска |
| **Ротация refresh-токенов** | При каждом обновлении: старый refresh отзывается, выдаётся новая пара; повторное предъявление старого — сброс всей сессии | Испорченный абонемент изымается, а попытка предъявить его повторно аннулирует все абонементы клиента |
| **RBAC** | Права выдаются ролям (student / cook / courier / admin), а не конкретным людям | Ключ выдаётся по должности, а не по фамилии |
| **IDOR** | Уязвимость: сервер доверяет чужому идентификатору и не проверяет владельца (пример: отменить чужой заказ, подставив `order_id`) | Кто угодно дёргает ручку чужой ячейки, а она открывается |
| **bcrypt** | Необратимое хеширование пароля с солью; в БД хранится только хеш | Из хеша пароль не восстановить, но при входе его легко сверить: ввели пароль — хеши совпали |
| **Rate limiting** | «Не больше 5 попыток входа за минуту с одного IP» → HTTP 429 | Турникет: шестой подряд отправляют обратно (429) |
| **Cache-Aside (ЛР № 4)** | Чтение: сначала Redis; попали (hit) — отдаём из кеша, мимо (miss) — идём в БД и сохраняем результат в кеш с TTL | Стенгазета с меню: смотрят все в неё, а кухню тревожат только раз в 5 минут |
| **Событийная инвалидация** | При изменении меню ключи кеша сбрасываются сразу, не дожидаясь TTL | В меню поменяли цену — старую стенгазету сняли прямо сейчас, а не через 5 минут |
| **Cache stampede** | TTL протух, и все запросы разом бьют в базу («лавина») — лечится локом: в базу идёт один, остальные ждут готовый кеш | Одновременно кончился кофе в автомате — очередь к кофейне вместо очереди к кассе |
| **CORS** | Браузерный фильтр: с чужих доменов наши запросы отклоняются | Пропускной режим для внешнего транспорта |
| **Secure by Default** | Безопасная конфигурация из коробки: секреты в `.env`, CORS закрыт, Swagger выключен в проде | Новоселье: замок уже стоит, дефолтный код меняешь при переезде |
| **Fail-open** | Если Redis недоступен, rate limit пропускает запрос, а не валит сервис | Турникет сломался — двери открывают, а не запирают всех |
| **Сброс сессии** | Если refresh-токен скомпрометирован, у пользователя отзываются ВСЕ refresh-токены | Потерялся один ключ — меняются замки во всём доме |
| **TestClient** | Python-инструмент: делает HTTP-запросы к приложению без запуска реального сервера | «Фиктивный клиент» для автотестов |

## 3. Как работает проект: файлы и роли

```
sirius_food/
├── app/
│   ├── main.py               # сборка приложения: роутеры, CORS, Swagger (=DEBUG=True), seed ролей, _cache_warmup на старте
│   ├── database.py           # движок SQLAlchemy: URL из настроек, SQL_ECHO для демонстрации
│   ├── models.py             # ORM-таблицы: User(+password_hash, role_id), Role, RefreshToken, MenuCategory, MenuItem(+category_id), Order, Delivery
│   ├── schemas.py            # Pydantic-схемы. В OrderCreate НЕТ user_id — идентификация только по токену!
│   ├── core/
│   │   ├── config.py         # Settings из .env: SECRET_KEY обязателен, DEBUG, REDIS_URL, ALLOWED_ORIGINS, CACHE_ENABLED
│   │   ├── jwt.py            # create_access_token (15 мин), create_refresh_token (7 дней), decode
│   │   ├── security.py       # bcrypt: hash_password / verify_password
│   │   ├── dependencies.py   # get_current_user (401/403), require_role (403) — «кто ты» и «что можно»
│   │   ├── rate_limit.py     # rate_limit(5,60): счётчик Redis по IP+путь → 429; fail-open
│   │   ├── redis.py          # общий клиент Redis: rate limiting + кеш (ЛР № 4)
│   │   └── exceptions.py     # доменные: NotFoundError(404), ForbiddenError(403), BusinessRuleError(400)
│   └── modules/
│       ├── auth/             # router/service/repository: логин и РОТАЦИЯ refresh-токенов
│       ├── users/            # register (bcrypt + роль student), topup (IDOR: только свой баланс, либо admin)
│       ├── menu/             # чтение — Cache-Aside на Redis (repository.py); мутации — cook|admin; invalidate_cache в service.py
│       ├── orders/           # create (id из JWT), cancel (IDOR в Service), kitchen/orders (роль cook)
│       └── delivery/         # assign (admin), complete/my (courier + IDOR в Service)
├── alembic/versions/         # миграции: roles/refresh_tokens (ЛР № 3), menu_categories (ЛР № 4)
├── locustfile.py             # сценарий нагрузочных тестов Locust (ЛР № 4)
├── tests/                    # 91 тест, см. § 5.3, § 6.7 и § 7
├── docs/locust/              # CSV-результаты замеров «до/после»
├── .env / .env.example       # секреты вне кода (Secure by Default)
├── docker-compose.yml        # PostgreSQL и Redis
└── README.md                 # отчёт с диаграммами, таблицей критериев и замерами
```

Правило чтения файла: `router.py` может смотреть только на HTTP, `service.py` — только на Python, `repository.py` — только на таблицы.

> На защите показать: «В `service.py` нет ни одного слова `fastapi` или `sqlalchemy`, а в `router.py` нет ни одного ORM-запроса `.query(`. Это проверяется не глазами, а тестом `tests/test_architecture.py` через разбор AST».

## 4. Подготовка окружения к демонстрации

### 4.1. Перед показом

```powershell
# 1) Запустить Docker Desktop (дождаться, пока не появится зелёный статус)
# 2) Поднять базы
cd C:\sirius_food
docker compose up -d db redis
docker exec sirius_food-db-1 pg_isready -U sirius   # ждём: accepting connections

# 3) Активировать окружение и поднять сервер
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload
```

Проверка готовности:
- `http://127.0.0.1:8000/docs` открывается (благодаря `DEBUG=True` в `.env`);
- в терминале сервера сыпятся SQL-запросы (это `SQL_ECHO`, пригодится для демонстрации слоёв).

Если порт 5432 занят локальным PostgreSQL — не страшно: контейнер живёт на **5433** (в `.env` указан `DB_PORT=5433`, `docker-compose.yml` это подхватывает).

### 4.2. Если база ещё не мигрирована (свежий клон)

```powershell
alembic upgrade head   # создаст roles, refresh_tokens, password_hash, раздаст роли
```

Для пустой базы `main.py` сам сеет четыре роли при старте; Alembic нужен, когда база уже частично заполнена.

### 4.3. Создать демо-пользователей

Регистрация всегда создаёт роль `student`, поэтому повара и админа делаем напрямую в базе (на защите честно сказать: роль назначена SQL-скриптом, само API регистрирует студентов):

```powershell
# Сначала через Swagger создать пользователей:
# POST /users/register  {"email":"cook@mail.ru",  "password":"SuperPass123"}
# POST /users/register  {"email":"admin@mail.ru", "password":"SuperPass123"}
# POST /users/register  {"email":"student2@mail.ru","password":"SuperPass123"}

# Потом повысить роли:
docker exec sirius_food-db-1 psql -U sirius -d sirius_food -c "UPDATE users SET role_id=(SELECT id FROM roles WHERE name='cook') WHERE email='cook@mail.ru';"
docker exec sirius_food-db-1 psql -U sirius -d sirius_food -c "UPDATE users SET role_id=(SELECT id FROM roles WHERE name='admin') WHERE email='admin@mail.ru';"

# Проверка:
docker exec sirius_food-db-1 psql -U sirius -d sirius_food -c "SELECT u.email, r.name AS role FROM users u JOIN roles r ON r.id=u.role_id;"
```

Также в Swagger создать одно блюдо (`POST /menu/items` под cook): `{"name":"Борщ","price":150}`.

## 5. Демонстрация ЛР № 2 (Clean Architecture)

### 5.1. Показать структуру (1 минута)

Открыть в редакторе три файла модуля `orders` рядом:

- `app/modules/orders/router.py`
  — «Только транспорт: HTTPException, Depends, вызов сервиса. Никаких запросов в базу»;
- `app/modules/orders/service.py`
  — «Только Python: бизнес-правила, доменные исключения (ValueError-наследники). Нет fastapi/sqlalchemy. Контракт репозитория — Protocol»;
- `app/modules/orders/repository.py`
  — «Единственный файл модуля, который знает SQLAlchemy. Зато и таблицы».

Основной тезис: **если завтра Postgres заменим на MongoDB, мы напишем новый `repository.py`, а `service.py` и `router.py` не изменятся вовсе**.

### 5.2. Показать SQL-логи (доказательство слоёв)

Один запрос `POST /orders/create` в терминале виден по шагам:

1. SELECT users / SELECT menu_items — repository достаёт пользователя и блюдо;
2. после бизнес-проверок в Сервисе — UPDATE users (списание баланса) и INSERT INTO orders — **в одной COMMIT-транзакции**.

Фраза: «Списание баланса и создание заказа — одна транзакция. Если бы, как в шаблоне методички, `update_user_balance` коммитил сразу, а сервер бы упал между двумя коммитами, студент остался бы без денег и без еды. Мы это исправили».

### 5.3. Показать инверсию зависимостей (критерий 10: подстановка Лисков)

В `app/modules/orders/service.py`:

```python
class OrderRepositoryProtocol(Protocol):
    def get_user_by_id(self, user_id: int): ...
    def save_order(self, user_id: int, item_id: int, quantity: int) -> int: ...
    # и другие методы-контракты

class OrderService:
    def __init__(self, repository: OrderRepositoryProtocol):
        self.repository = repository   # внедрение зависимости через конструктор
```

- В `router.py` — конкретная реализация `OrderRepository(db)` (там, где решаем, что хранилище — Postgres).
- В unit-тестах — in-memory-заглушка с тем же контрактом: тот же `OrderService(repository=fake)`, при этом postgres не импортирован вообще.

Команда для доказательства:

```powershell
python -m pytest tests/test_orders_service.py tests/test_users_service.py tests/test_auth_service.py tests/test_architecture.py -v
```

Фраза: «Мы подменили реализацию хранилища на заглушку, не изменив ни строки в `service.py` и `router.py`. Это и есть принцип подстановки Барбары Лисков в действии: любая реализация контракта взаимозаменяема для сервиса».

### 5.4. Показать архитектурный тест

`tests/test_architecture.py` разбирает каждый `service.py` через AST и падает, если там появились `fastapi` / `sqlalchemy` / `starlette` или обращение service → repository. Фраза: «Это тест, который охраняет само архитектурное правило: через полгода никто не сможет незаметно вернуться к MVP-стилю».

### 5.5. Показать git-историю (процесс рефакторинга)

```powershell
git log --oneline
```

Видны шаги из методички: `orders: шаг 1 — repository`, `шаг 2 — service`, `шаг 3 — router`, затем то же для `users`.

## 6. Демонстрация ЛР № 3 (безопасность)

Эндпоинты и доступ:

| Эндпоинт | Роль | Примечание |
|---|---|---|
| `POST /users/register` | аноним | bcrypt + роль student |
| `POST /auth/login` | аноним | логин + пароль → пара токенов; rate limit 5/мин |
| `POST /auth/refresh` | с токеном | старый refresh → НОВАЯ пара токенов |
| `POST /users/{id}/topup` | владелец (или admin) | IDOR-защита в Service |
| `POST /orders/create` | любой с JWT (id из токена) | user_id из payload игнорируется |
| `POST /orders/{id}/cancel` | владелец заказа | IDOR-защита в Service |
| `GET /orders/kitchen/orders` | cook | RBAC |
| `POST /menu/items`, `PATCH /menu/items/{id}` | cook, admin | RBAC |
| `POST /delivery/assign` | admin | RBAC |
| `PATCH /delivery/{id}/complete` | courier (владелец доставки) | RBAC + IDOR |
| `GET /delivery/my` | courier | только свои доставки |

### 6.1. Сценарий 1: без токена → 401

В Swagger открыть `POST /orders/create`, вбить `{"item_id":1,"quantity":1}` и нажать Execute **без Authorization**.

Ожидаем: `401 Unauthorized` (`{"detail":"Not authenticated"}`).

Фраза: «Эндпоинт закрыт через `Depends(get_current_user)`: без подписанного сервером токена запрос даже не дойдёт до бизнес-логики».

### 6.2. Сценарий 2: полноценный вход → успешный заказ

1. `POST /users/register` `{"email":"s@mail.ru","password":"SuperPass123"}` → `{"status":"success","user_id":1,"email":"s@mail.ru"}`.
2. `POST /auth/login` → получить `{"access_token":"eyJ…","refresh_token":"eyJ…","token_type":"bearer"}`.
3. Скопировать `access_token`. В правом верхнем углу Swagger нажать **Authorize**, вставить токен.
4. `POST /users/1/topup?amount=1000` → `{"status":"success","new_balance":1000.0}`.
5. Идентификация взята из JWT, а не из payload: раньше клиент мог писать в запросе `user_id` кого угодно, теперь в схеме `OrderCreate` этого поля нет вовсе (`app/schemas.py`).
6. Под cook создать блюдо, затем `POST /orders/create` `{"item_id":1,"quantity":2}` → `{"status":"success","order_id":1}`.

Показать в терминале: UPDATE баланса и INSERT заказа — «то же самое, что в ЛР № 2, но теперь за каждым запросом стоит проверенный человек».

### 6.3. Сценарий 3: IDOR → 403 (чужой заказ)

1. Под студентом 1 создать заказ (например `order_id=1`).
2. Зарегистрировать/залогинить `student2@mail.ru`, взять его `access_token`.
3. Под студентом 2: `POST /orders/1/cancel`.

Ожидаем: `403 Forbidden`, `{"detail":"Можно отменять только свои заказы"}`.

Фраза: «Это защита от IDOR. Важная деталь: проверка `order.user_id != current_user.id` находится в `OrderService.cancel_order`, а не в роутере. Это бизнес-правило: оно одинаково для HTTP, для CLI и для фонового воркера. Роутер лишь переводит `ForbiddenError` в HTTP 403».

### 6.4. Сценарий 4: RBAC → 403 (студент на кухне)

- Под студенческим токеном: `GET /orders/kitchen/orders` → `403 Forbidden`, `{"detail":"Доступ запрещён"}`.
- Под токеном cook (см. § 4.3): тот же запрос → **200** со списком заказов.
- Дополнительно: `POST /menu/items` студентом → 403, поваром → 200.

Фраза: «Аутентификация прошла (мы знаем, кто постучался), но авторизация сказала "нет". Различие кодов: 401 — не знаем, кто ты, перелогинься; 403 — знаем, но допуск нет».

### 6.5. Сценарий 5: rate limiting → 429

Шесть раз подряд `POST /auth/login` с неверным паролем:

```powershell
curl.exe -X POST "http://127.0.0.1:8000/auth/login" -H "Content-Type: application/json" -d "{\"email\":\"s@mail.ru\",\"password\":\"wrong\"}"
```

Ожидаем: пять раз `401`, на шестой — `429` `{"detail":"Слишком много запросов. Попробуйте позже"}`.

Показать содержимое Redis (счётчик там):

```powershell
docker exec sirius_food-redis-1 redis-cli KEYS "rate_limit:*"
docker exec sirius_food-redis-1 redis-cli TTL "rate_limit:<тот-ключ>"
```

Фраза: «Счётчик не в памяти Python, а в Redis. Если сервер запущен в нескольких репликах, в памяти каждой свой счётчик — атакующий обойдёт лимит, прыгая между репликами. Redis — общий для всех. Если Redis вдруг недоступен — сознательно fail-open: приложение продолжает работать, просто без ограничения; это покрыто юнит-тестом».

### 6.6. Сценарий 6: ротация refresh-токенов (критерий 10)

1. Логинимся, копируем `refresh_token`.
2. `POST /auth/refresh` `{"refresh_token":"<старый>"}` → `200`, в ответе **новая пара** (новый `refresh_token` ≠ старый) — это ротация.
3. Повторить тот же запрос еще раз со старым refresh → `401`, сообщение «Сессия сброшена, войдите заново».
4. И только что выданный (в п. 2) refresh тоже больше не работает → `401`: сессия стёрлась целиком.

Показать в БД: `SELECT user_id, is_revoked FROM refresh_tokens;` — все токены пользователя `is_revoked=true`.

Фраза: «Если злоумышленник украл refresh-токен и попытается им воспользоваться, система расценивает это как взлом и аннулирует ВСЮ сессию пользователя — включая токен, только что выданный легитимному владельцу. Сами refresh-токены в БД хранятся только как SHA-256-хеш: даже при утечке таблицы действующие токены не восстановить». Код: `app/modules/auth/service.py` → `AuthService.refresh`, `app/modules/auth/repository.py` → `revoke_user_tokens`.

## 7. Демонстрация ЛР № 4 (кеширование Redis)

Все команды Redis: `docker exec sirius_food-redis-1 redis-cli <команда>`.
Открыть в редакторе: `app/modules/menu/repository.py` (весь кеш здесь), `app/modules/menu/service.py` (только `invalidate_cache`), `app/core/redis.py`, `app/main.py` (прогрев).

### 7.1. Сценарий 1: Cache-Aside + событийная инвалидация (критерии 6–7)

1. В Swagger `GET /menu/items` → 200, список блюд.
2. `redis-cli GET menu:all` → в кеше лежит JSON меню; `redis-cli TTL menu:all` → ≤ 300 секунд. Это **miss → БД → запись в кеш** с первого раза (или прогрев на старте).
3. Повторный `GET /menu/items` при `SQL_ECHO=True` в `.env`: в консоли сервера **нет нового SELECT из menu_items** — это hit, БД не тронута.
4. `POST /menu/items` (cook, токен) → сразу после ответа `redis-cli EXISTS menu:all` → `0`: **событийная инвалидация** удалила ключ при мутации, не дожидаясь TTL.
5. Повторный `GET /menu/items` → новое блюдо видно **сразу**; ключ заново прогрет (`EXISTS menu:all` → `1`).

Фраза: «Читатель сначала смотрит в Redis; на hit БД вообще не вызывается. Пишет сервис via репозиторий, и после сохранения мы не ждём, пока протухнет TTL, а сами сбрасываем ключи — так меню всегда актуально».

### 7.2. Сценарий 2: категории с другим TTL (критерий 10)

1. `GET /menu/categories` и `GET /menu/categories/1` → 200.
2. `redis-cli TTL menu:category:1` → до **600**, а `redis-cli TTL menu:all` → до **300**. Разные TTL — осознанное решение: категории меняются ещё реже, чем блюда.
3. `PATCH /menu/items/{id}` (cook) → `redis-cli EXISTS menu:all` → 0 и `redis-cli EXISTS menu:category:1` → 0: инвалидируются **все** ключи меню (категории ищутся по шаблону `menu:category:*` через scan).

### 7.3. Сценарий 3: прогрев кеша (критерий 10)

1. Рестарт сервера (`Ctrl+C` → `uvicorn app.main:app --reload`).
2. До первого запроса: `redis-cli TTL menu:all` → близко к 300 — ключ заполнен **стартовым событием**, а не запросом.
3. Фраза: «Cache warm-up: после деплоя первый посетитель получает меню из Redis, минуя базу — нет "холодного" miss на обеденном пике».

### 7.4. Сценарий 4: защита от cache stampede (критерий 9)

Показать код `menu/repository.py` → метод `_cache_aside`.

Фраза: «Когда TTL истёк и 500 пользователей пришли одновременно, без защиты все 500 ушли бы в PostgreSQL. Мы берём distributed-лок `menu:all:lock`: успевший первым идёт в БД и греет кеш; остальные ждут до 3 секунд, после захвата лока **повторно** проверяют кеш (double-check) — и most читают уже прогретый ключ. Лок с timeout 10 секунд, чтобы зависший запрос не заблокировал меню навсегда. Если Redis недоступен — fail-open: читаем из БД, приложение медленнее, но живо».

### 7.5. Сценарий 5: замеры «до/после»

1. Нагрузить кеш (Users 500, Spawn rate 10):

```powershell
python -m locust -f locustfile.py --host=http://127.0.0.1:8000 --headless --only-summary -u 200 -r 10 -t 30s
```

2. Перезапустить сервер с `$env:CACHE_ENABLED="false"` («до кеша») и прогнать снова — сравнить RPS/медианы.
3. Показать таблицы в README § 3 и CSV в `docs/locust/`.

Фраза-оговорка (честность ценится на защите): «При 50 пользователях база и так отвечает быстро, поэтому кеш заметнее улучшает хвосты (95-й перцентиль −20%, 99-й −23%), а медиану — слабо. При 500 пользователях медиана и среднее улучшаются на 20–24%, потому что кеш снимает запросы к PostgreSQL; полностью эффект не виден, так как узким местом становится пул потоков одного uvicorn-воркера, а не база. На проде с несколькими воркерами эффект кеша выражен сильнее».

### 7.6. Где НЕ кешируем и почему

`GET /users/me`, балансы, заказы, токены — персональные и меняющиеся данные; ошибка кеша здесь = чужие деньги или чужой заказ (IDOR через кеш). Кешируем только **публичный каталог**: меню и категории.

## 8. Ответы на контрольные вопросы

### ЛР № 2

**1. Какому кругу Мартина соответствует `repository.py`?**
Кругу 3 — Interface Adapters. Репозиторий — адаптер, который переводит вызовы бизнес-логики в конкретную технологию (SQLAlchemy → SQL выбранной СУБД). Он стоит между внутренней логикой (круги 1–2) и Frameworks & Drivers (круг 4): сам о фреймворке БД знает, но никто из внутренностей к нему напрямую не обращается — только через контракт.

**2. Почему в `service.py` запрещены `fastapi` и `sqlalchemy`?**
Это правило зависимостей (The Dependency Rule): исходный код зависимостей направлен только внутрь. Сервис — ядро домена; если в него попадает `HTTPException` или `Session`, то веб-фреймворк и СУБД «прошивают» бизнес-логику, и при замене периферии (например, FastAPI → другой фреймворк) придётся переписывать ядро. Разделение сделано так, что сервис можно переиспользовать в CLI, тестах и фоновому воркере.

**3. Где проверяется формат email, а где — уникальность?**
Формат — транспортный слой (Pydantic, `EmailStr` в схеме): это техническое правило, не требующее состояния приложения. Уникальность — Service: это бизнес-правило, требующее обращения к хранилищу (`get_user_by_email`). Критерий разделения: если проверку можно сделать без БД и вне контекста — транспорт; если нужна информация о состоянии мира — Service.

**4. Что такое Dependency Inversion Principle и как реализован?**
Модули верхнего уровня не должны зависеть от модулей нижнего; оба должны зависеть от абстракций. Реализовано так: `service.py` объявляет `OrderRepositoryProtocol(Protocol)` и типизирует им параметр конструктора: `__init__(self, repository: OrderRepositoryProtocol)`. Любая реализация контракта (Postgres-реализация, in-memory-заглушка) передаётся снаружи. Зависимость от абстракции, а не от класса.

**5. Замена PostgreSQL на MongoDB: что меняется, что нет?**
Меняются: файлы `app/modules/*/repository.py` (новая реализация контракта), `app/database.py` / `app/core/config.py` (подключение), `docker-compose.yml`, схема миграции. Не меняются: все `service.py` и `router.py`, Pydantic-схемы, unit-тесты сервисов (они уже на заглушках), архитектурный тест. Именно поэтому рефакторинг окупился.

**6. Переиспользование `OrderService` в CLI/Celery?**
Да, свободно. Пример в CLI:

```python
service = OrderService(OrderRepository(db))   # та же сборка, что в router
service.create_order(user_id=5, item_id=2, quantity=1)
```

Ничего HTTP-специфичного в сервисе нет, исключения — доменные. Именно так работают наши unit-тесты: они по сути и есть «CLI-клиенты» сервиса.

**7. Техническая vs бизнес-валидация?**
Техническая — про формат и корректность передачи данных: «quantity — целое число больше 0», «email похож на email», «phone длиннее 10 символов». Бизнес — про правила предметной области: «хватит ли денег на балансе», «имя блюда свободно?», «заказ можно отменять только свой», «максимум пополнения 50 000 ₽». Техвалидиция обычно в схемах/роутере; бизнес — в Service, потому что требует хранилища.

**8. Что нарушает «service.py импортирует HTTPException из fastapi для возврата ошибки 400»?**
Dependency Rule (правило зависимостей): бизнес-слой получает зависимость от Frameworks & Drivers. Возврат HTTP-кода — не доменное понятие. Правильный приём: Service выбрасывает доменное исключение (у нас `BusinessRuleError`), а трансляцию в HTTP-статус оставляет router.

### ЛР № 3

**1. Чем аутентификация отличается от авторизации? Ошибки на каждом уровне.**
Аутентификация — установить личность («кто ты»): логин+пароль → JWT. Авторизация — решить, что можно («что тебе можно»): `require_role("cook")`, владелец ли объекта. Ошибка аутентификации — злоумышленник выдаёт себя за другого (пример: не сверили хеш пароля). Ошибка авторизации — легальный пользователь получает доступ к чужим данным (классический IDOR: `cancel_order` без проверки владельца).

**2. Почему `user_id` убирают из payload?**
Payload — недоверенный источник: клиент мог прислать чужой `user_id` и действовать от его имени. Токен подписан сервером, поэтому `sub` из JWT доверен. В `OrderCreate` поле `user_id` удалено вовсе; в `create_order` всегда используется `current_user.id`. Тест `test_create_order_ignores_user_id_from_payload` показывает, что чужое `user_id` в запросе просто игнорируется.

**3. Что такое IDOR и где от него защита?**
IDOR (Insecure Direct Object Reference) — сервер доверяет клиентскому идентификатору и не проверяет принадлежность объекта. Защита — в Service-слое, потому что проверка «этот объект мой?» — бизнес-правило: надо сравнить `order.user_id` из хранилища и текущего пользователя из токена. Так правило переиспользуется в HTTP/CLI/воркере и тестируется без сервера (`tests/test_orders_service.py::CancelOrderTests`). Роутер только транслирует `ForbiddenError` в HTTP 403.

**4. Почему payload JWT нельзя считать защищённым?**
Payload лишь закодирован в Base64, это не шифрование. Подпись гарантирует целостность («не подделан»), но не конфиденциальность: любой, кто перехватил токен, прочитает содержимое (header.payload.signature легко декодировать). Поэтому в payload нет пароля и персональных данных — только `sub`, `exp`, `type`, `jti`.

**5. Почему проверка роли — в API-слое, а право на объект — в Service?**
Роль — свойство внешний точки входа: файл «cook» для конкретного эндпоинта (`require_role("cook")` на `GET /orders/kitchen/orders`). Это «двери» — они проверяются при входе. Право на конкретный объект («мой ли это заказ?») — бизнес-правило над данными: Service. Так разделение ответственности честное: доступ по роли — на входе (в роутере), тонкая проверка владения — в бизнес-логике.

**6. Зачем rate limiting на Redis, а не в памяти?**
В памяти каждый экземпляр сервера имеет свой счётчик: у атакующего будет 5 попыток на каждую реплику (суммарно 5×N). Redis — общее состояние для всех реплик, попытки считаются глобально. Плюс TTL (`expire`) в Redis автоматически сбрасывает счётчик по завершении окна. Если Redis недоступен — fail-open с warning-логом, чтобы не ронять вход в приложение.

**7. Что такое Secure by Default? Три примера из проекта.**
Принцип: из коробки система уже безопасна; дефолт — не «небезопасно, но можно включить защиту». Примеры: (1) секреты из `.env`, при отсутствии `SECRET_KEY` запуск невозможен; (2) CORS ограничен списком `ALLOWED_ORIGINS`, не `*`; (3) Swagger отключён при `DEBUG=False` (`/docs` → 404); (4) пароли только bcrypt-хеш, refresh-токены только SHA-256-хеш.

**8. Что нарушает «service.py импортирует HTTPException из fastapi для возврата ошибки 403»?**
Dependency Rule (то же, что в ЛР № 2): Service сигналит доменным исключением `ForbiddenError`, роутер переводит его в HTTP 403. Иначе бизнес-логика связывается с transport и не переиспользуется без HTTP.

### ЛР № 4

**1. Почему логика кеширования в Repository, а не в Service? Как это связано с Clean Architecture?**
Кеш — деталь **хранения** (ускоритель СУБД), а не бизнес-правило. По правилу зависимостей внешние слои зависят от внутренних, но внутренние ничего не знают о периферии: «данные из Redis или из Postgres» для бизнес-логики неотличимо — сервис просто вызывает `repository.list_items()`. Если кеш переехал бы в Service, зависимость от Redis протекла бы во внутренний круг, сервис стало бы нельзя переиспользовать без Redis (CLI, фоновый воркер, тесты), а смену кеша на Memcached пришлось бы делать правкой бизнес-логики. Наш архитектурный AST-тест прямо запрещает импорт `redis` в `service.py`; инвалидация выполняется вызовом `repository.invalidate_cache()` по контракту.

**2. Что такое Cache-Aside и какие у неё недостатки?**
Схема: приложение сначала смотрит в кеш; на hit возвращает данные из Redis; на miss читает БД, **само** кладёт результат в кеш с TTL и отвечает. Кеш не обновляется БД — приложение управляет им вручную. Недостатки: (1) окно устаревания — между мутацией и инвалидацией/TTL читатели получают старое (лечится событийной инвалидацией); (2) «холодный» старт — пустой кеш даёт лавину miss (treatment: прогрев на старте); (3) лишний сетевой round-trip на каждый запрос; (4) при инвалидации с ошибкой данные висят устаревшими до истечения TTL (поэтому TTL всё равно ставим); (5) в multi-node сценарии инвалидация должна быть видна всем репликам — поэтому Redis общий, а не память процесса.

**3. Что произойдёт, если Redis перезагрузится во время пиковой нагрузки? Как это называется?**
Кеш опустеет; все запросы одновременно станут miss и хлынут в PostgreSQL — «cache stampede» (лавина/cache herd): переполнение пула соединений, секунды латентности, возможно падение БД. У нас два слоя защиты: distributed-лок per-key (один запрос греет кеш, остальные ждут и читают готовый) и fail-open (сам Redis мог бы и умереть в этот момент — тогда приложение честно читает из БД, медленнее, но не падает). После рестарта Redis ключи прогреваются первым же читателем (miss → БД → кеш) либо warm-up'ом при старте приложения.

**4. Почему TTL 5 минут, а не 1 час?**
Компромисс hit-rate ↔ свежесть. Меню меняется непредсказуемо (повар снял блюдо, поменял цену) — часовой TTL дал бы час устаревших данных для всех, кто не попал в окно инвалидации. 5 минут ограничивают максимальное окно устаревания, при том что меню читается сотни раз в минуту: hit-rate при 5-минутном TTL всё равно почти 100% (за 5 минут несколько тысяч читов вместо одной загрузки). Категории меняются ещё реже — им дано 10 минут.

**5. Как событийная инвалидация дополняет инвалидацию по TTL?**
Они закрывают слабости друг друга. События (удаление ключей в `invalidate_cache()` после `create_item`/`update_item`) дают мгновенную свежесть после наших мутаций. TTL — страховка на случай, когда событие не сработало: баг в коде, мутация в обход приложения (psql-скрипт, миграция, второй инстанс приложения), потеря сообщения — устаревший кеш протухнет максимум через TTL. Осознанный дизайн: события ради консистентности, TTL ради отката при ошибках.

**6. Какие данные в «Сириус.Еде» категорически нельзя кешировать и почему?**
Балансы пользователей: деньги меняются извне (пополнение, списание за заказ) — показ старого баланса = финансовая ошибка или возможность overspend. Заказы и их статусы: персональные данные, при утечке кеша на shared-ключе это IDOR через кеш, плюс статусы меняются кухней и курьером. Сессии/refresh-токены и проверки прав: отзыв токена должен действовать мгновенно — кешированное «да, он валиден» наносит прямой ущерб безопасности. Общий принцип: кешируются публично читаемые, редко меняющиеся данные (меню и категории); всё то, где важно «кому» или где много мутаций, — не кешируется вовсе.

**7. Как бы вы решили проблему cache stampede, если бы кеш хранил 10 000 ключей?**
Пер-ключевой лок (как у нас) — база, но при 10 000 ключей есть масштабные сценарии: рестарт Redis опустошает все 10 000 разом, и 10 000 локов не спасут от 10 000 одновременных волн промахов. Дополнительно: (1) **прогрев при старте** (у нас: `warm_cache()` заполняет горячие ключи до открытия трафика); (2) **jitter TTL** — рассеять время истечения по 10 000 ключам (например ±10%), чтобы они не протухали синхронно; (3) **вероятностное досрочное обновление** (XFetch: обновлять ключ заранее с вероятностью, пропорциональной времени до истечения и времени перегенерации); (4) фоновый воркер, который сам перегенерирует горячие ключи до их TTL, а читатели никогда не видят miss.

## 9. Вопросы «на засыпку» (и краткие ответы)

| Вопрос | Короткий ответ |
|---|---|
| Почему SHA-256 от refresh-токена, а не сам токен? | При утечке базы хеш однонаправлен: восстановить действующий токен нельзя. |
| Почему не `allow_origins=["*"]` с `allow_credentials=True`? | Опасная комбинация: любой сайт сможет слать запросы от имени пользователя с его cookie/заголовками. Поэтому список ограничен. |
| Что произойдёт, если Redis упадёт? | `ConnectionError` перехвачен — fail-open, запросы продолжают работать (лог warning). Тест `test_unavailable_redis_fails_open`. |
| Что произойдёт, если просрочен access-токен? | `try_decode_token` вернёт `None` → 401. Клиент должен вызвать `/auth/refresh`. |
| Что произойдёт, если просрочен refresh-токен? | Запись не будет считаться активной → 401. Новый refresh не выдать — только перелогиниться. |
| Зачем `jti` в JWT, если он не проверяется? | Гарантия уникальности токенов (два access, выданных за одну секунду, различаются); поле пригодится для чёрных списков токенов. |
| Где проверять, что цена положительная? | Техническая валидация: Pydantic-схема/роутер (не требует БД). Уникальность названия — Service (нужно хранилище). |
| Почему bcrypt, а не MD5/SHA-256? | bcrypt медленный и с солью — устойчив к радужным таблицам и брутфорсу. SHA-256 слишком быстрый для паролей (но хорош для хешей длинных случайных строк вроде refresh-токенов). |
| Почему 401 и 403 разные? | 401 = «не знаем, кто ты» — повторить вход с теми же данными можно. 403 = «знаем, но нельзя» — перелогин не поможет. |
| Чем Protocol лучше ABC из методички? | Дает тот же эффект (структурная типизация без наследования): контракт объявлен в `service.py`, реализации не обязаны это делать — не нужно менять код. Для критерия 9 («ABC с двумя реализациями») это эквивалентно, а LSP — наболее прагматично. |
| Случай, когда роль должна проверяться в Service, а не в роутере? | Если право зависит от данных объекта: «администратор может пополнить чужой баланс» — его можно в Service (см. `top_up_balance`). |
