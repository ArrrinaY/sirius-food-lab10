# ЛР № 6. Вынос модуля delivery в gRPC-микросервис — шпаргалка для защиты

Проект: «Сириус.Еда» · Слой: микросервис `delivery` (gRPC) · Оценка: 10 баллов

---

## 1. Зачем выносить модуль в сервис (паттерн Strangler Fig)

Монолит с ростом команды превращается в проблему:

* одно приложение деплоится **целиком** — правка мелочи = полный релиз;
* падение одного модуля роняет всё;
* масштабировать можно только всё приложение сразу, хотя «доставка» может требовать иных ресурсов, чем «меню».

**Strangler Fig («душитель»)** — не переписывать систему с нуля, а **вырезать модули по одному**, перенаправляя трафик на новые сервисы, пока старый монолит не «задушен» полностью.

Почему `delivery` — идеальный первый кандидат:

1. **Слабая связанность** — никто в монолите не читает таблицу `deliveries` напрямую;
2. **Понятная граница** — 3 операции (assign / complete / список), чёткий домен;
3. **Малый риск** — при сбое страдает только трекинг доставки, заказы и меню живут дальше.

Что вырезано: транспорт модуля. FastAPI больше **не знает про таблицу** `deliveries` — маршруты ходят через gRPC-клиент. Всё приложение продолжает работать (это и есть суть паттерна: миграция без остановки).

---

## 2. Почему gRPC, а не HTTP/JSON

| Возможность | gRPC | REST/JSON |
|-------------|------|-----------|
| Транспорт | **HTTP/2**: мультиплексирование, один TCP-канал на много параллельных запросов | HTTP/1.1 — соединение на запрос (или keep-alive без стримингов) |
| Формат | **Protocol Buffers** — бинарный, компактный, быстрый парсинг | JSON — текстовый, избыточный |
| Контракт | **`.proto` — источник правды**: из него генерируются и сервер (Servicer), и клиент (Stub) — разойтись по интерфейсу физически нельзя | контракт «по договорённости», проверяется только в рантайме |
| Стриминги | из коробки: Server Streaming, Bidirectional Streaming | пришлось бы городить SSE/WebSocket поверх |
| Строгая типизация | да, поля и типы в контракте | нет |

## 3. Ступеньки выполнения (по методичке)

1. **Контракт** — `proto/delivery.proto`: 6 RPC.
2. **Генерация** — `python -m grpc_tools.protoc -Iproto --python_out=. --grpc_python_out=. proto/delivery.proto` → `delivery_pb2.py` + `delivery_pb2_grpc.py`.
3. **Сервер** — `delivery_server.py` (класс Servicer).
4. **Клиент** — `app/modules/delivery/grpc_client.py` (обёртка над Stub).
5. **Интеграция** — роутер FastAPI переключён с репозитория на gRPC-клиент.

---

## 4. Ключевое архитектурное решение

**Сервер НЕ переписывает бизнес-правила** (в отличие от шаблона методички, где логика дублировалась внутри `delivery_server.py`). Здесь Servicer — тонкий транспортный слой:

```
protobuf-запрос → Servicer → DeliveryService (правила) → DeliveryRepository (SQL)
                     ↓
     доменные исключения → статусы gRPC
```

Выгоды:

* правила «только оплаченный заказ», «один курьер — одна активная доставка», проверка IDOR живут **в одном месте** (`service.py`) — не разъезжаются при правке;
* `service.py` **не изменился вообще** — и не должен: он чистый (без fastapi/sqlalchemy/grpc), это Круги 1–2;
* gRPC стал просто ещё одним транспортом рядом с HTTP (как CLI или воркер Celery).

Порт и адрес: сервер и клиент читают `DELIVERY_SERVICE_HOST/PORT` из **одного источника** (`.env` → `app/core/config.py`). Порт 50061, а не канонический 50051: на Windows с Hyper-V диапазон 50000–50059 зарезервирован (`netsh int ipv4 show excludedportrange protocol=tcp`), bind там невозможен — реальная находка при отладке.

## 5. Контракт: 6 RPC (4 unary + 2 streaming)

| RPC | Тип | Что делает |
|-----|-----|-----------|
| `AssignCourier` | unary | назначение курьера (роль admin проверяется на HTTP-слое) |
| `CompleteDelivery` | unary | завершение доставки; `courier_id` передаётся из JWT → IDOR-проверка на сервере |
| `GetDelivery` | unary | доставка по ID заказа |
| `ListDeliveries` | unary | список доставок курьера (для `GET /delivery/my`) |
| `TrackDelivery` | **Server Streaming** | сервер сам шлёт поток статусов `in_progress → on_the_way → delivered`, пауза 2 с |
| `ChatWithCourier` | **Bidirectional Streaming** | чат «клиент ↔ курьер» в открытом двустороннем канале |

Отступление от шаблона (обосновано): в `CompleteDeliveryRequest` добавлено поле `courier_id` — клиент берёт его из JWT. Так проверка «доставка принадлежит этому курьеру» (IDOR) осталась в Service-слое, а не выпала при смене транспорта. Добавлен и RPC `ListDeliveries`, которого не было в шаблоне — иначе `GET /delivery/my` пришлось бы оставить прямым доступом к БД, что ломает Strangler Fig.

## 6. Обработка сетевых ошибок (критерий 8) — три уровня маппинга

1. **Домен сервера → gRPC-статус** (`delivery_server.py::_abort`):

| Исключение | Статус gRPC |
|------------|-------------|
| `NotFoundError` | `NOT_FOUND` |
| `ForbiddenError` | `PERMISSION_DENIED` |
| `BusinessRuleError` | `INVALID_ARGUMENT` |

2. **gRPC-статус → исключение клиента** (`grpc_client.py::_handle_error`), каждый RPC под таймаутом 5 с (стриминг — 30 с):

| Статус gRPC | Исключение | Смысл |
|-------------|------------|-------|
| `NOT_FOUND` | `NotFoundError` | доставки нет |
| `PERMISSION_DENIED` | `ForbiddenError` | чужая доставка |
| `INVALID_ARGUMENT` | `BusinessRuleError` | нарушение бизнес-правила |
| `UNAVAILABLE` / `CANCELLED` | `ConnectionError` | сервис упал/недоступен |
| `DEADLINE_EXCEEDED` | `TimeoutError` | таймаут |
| прочие | `RuntimeError` | неизвестный сбой |

3. **Исключение → HTTP** (`router.py::_raise_http`): 404 / 403 / 400 / **503** / **504** / 500.

Зачем три уровня: статусы gRPC — транспортное соглашение между сервисами; исключения — язык домена; HTTP — то, что видит пользователь. Клиент не «проглатывает» причину сбоя, а честно транслирует её.

**Таймаут обязателен**: без него зависший вызов навсегда занимает поток uvicorn.

Проверено вживую: остановка `delivery_server.py` → `POST /delivery/assign` → **503** «Delivery service is unavailable», при этом FastAPI продолжает отвечать (логин 200); после перезапуска — снова 200.

## 7. Server Streaming — `TrackDelivery` (критерий 9)

**Unary** — «запрос → один ответ». **Server Streaming** — «запрос → серия ответов, которые сервер инициирует сам».

Для трека доставки поллинг дал бы N лишних запросов и лаг обновления; поток даёт:

* мгновенную доставку каждого статуса (`in_progress → on_the_way → delivered`, шаг 2 с);
* ноль лишнего трафика и ноль лишних запросов к БД.

Детали реализации:

* сервер — генератор: `yield delivery_pb2.DeliveryStatus(...)` с `time.sleep(2)`;
* `context.is_active()` перед каждым yield — ранний выход, если клиент отключился (не пишем «в никуда»);
* наружу отдано **SSE-эндпоинтом** `GET /delivery/{order_id}/track` (FastAPI `StreamingResponse`, `text/event-stream`): HTTP-клиент получает `data: {"status": "on_the_way", ...}` раз в 2 секунды.

Лог сервера при демо:

```
TrackDelivery order=11 → in_progress
TrackDelivery order=11 → on_the_way
TrackDelivery order=11 → delivered
```

## 8. Bidirectional Streaming — `ChatWithCourier` (критерий 10)

Обе стороны одновременно читают и пишут в один открытый канал — это уже не «запрос-ответ», а протокол диалога.

* клиент передаёт **генератор** исходящих сообщений; сервер итерирует входящий поток и на каждое сообщение `yield`-ит ответ, не закрывая канал;
* автоответы «курьера»: «где» → «Я в пути, буду через 10 минут»; «спасибо» → вежливый ответ; иначе — подтверждение приёма;
* полноценный интерактивный чат — `scripts/grpc_chat.py` (тестирующий скрипт из критерия);
* в Swagger показан «одношаговый» вариант `POST /delivery/{order_id}/chat`: одно сообщение кладётся в открытый канал, читается ответ, канал закрывается (HTTP не умеет полный duplex — это ограничение транспорта, а не gRPC).

## 9. Роль `grpc_client.py` в слоях

`DeliveryGrpcClient` — **инфраструктурный адаптер** (Круг 3), аналог репозитория:

* маршруты вызывают методы dict-in/dict-out, не зная о protobuf, каналах и таймаутах;
* единственное место, где живут таймауты и маппинг ошибок;
* **DI через конструктор**: `stub` инжектируется → 18 unit-тестов на fake-stub **без сети** (`tests/test_grpc_client.py`): все статусы ошибок, успешные пути, чтение обоих стримингов.

---

## 10. Честный компромисс: одна БД на два сервиса

Идеал микросервисов — каждый владеет своими данными. Сейчас и монолит, и микросервис работают с одной PostgreSQL:

* **почему допустимо**: это этап миграции Strangler Fig; оба наследуют один `DeliveryRepository` из одного кода;
* **следующий шаг**: выделить схему `deliveries` в отдельную БД — но тогда общие сущности (заказы) потребуют событийной синхронизации (как очереди Celery в ЛР № 5).

## 11. Демонстрация (сценарий защиты)

```bash
docker compose up -d db redis
python scripts/seed_lab6.py                             # admin/courier/student + оплаченный заказ
python delivery_server.py                               # терминал 1 — gRPC (50061)
python -m uvicorn app.main:app --port 8000              # терминал 2 — API
python scripts/demo_lab6.py                             # все RPC: 200/400/403 + SSE-трек
python scripts/grpc_chat.py <order_id>                  # bidi-чат; order_id печатает seed_lab6.py
# проверка 503: остановить delivery_server.py, затем:
python scripts/seed_lab6.py                             # сбросить заказ в paid
python scripts/check_503.py                             # логин 200, assign → 503
# перезапустить delivery_server.py и снова seed_lab6.py для чистого состояния
```

Результаты живого прогона: assign 200 → повторное assign 400 («у курьера уже есть активная доставка») → SSE-трек (3 статуса) → complete 200 → `/my` 200 → complete от студента 403 → повторное complete 400 → чат (2 ответа курьера) → стоп микросервиса → assign **503** → рестарт → assign 200.
